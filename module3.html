Let’s chat about a vibe-coding (🪱)

## Rationale

Fact - A: Coding is a gateway to lots of tools

It gives you access to:

  • Thousands of specialised R packages
  • Geospatial tools such as QGIS and PostGIS
  • Statistical and biometrics methods that are often only available through code
  • Access to database and data engineering tools

Fact - B: LLMs can write really good code (Module1)

(We discussed in module 1 so not dwelling on here but LLMs are really good at coding…)

Advantages

  • Trained on billions of lines of code, documentation, tutorials, and technical discussions
  • Have “seen” solutions to many common programming problems before
  • Can generate working code in seconds
  • Often better at spotting syntax errors than average programmers
  • Can use thousands of packages and functions that no human could memorise
  • coding is very logical/systematic…(perfect for machines)

Fact - C: You have a great idea

Coming up lots of ideas is often easy

But “testing riding them” (aka seeing if the idea is actually any good) can be a hurdle to every exploring them.

Given Fact A and Fact B, why not have LLMs write code for you so you can test ride those ideas (Fact C)?

Using LLM to write lowers the cost of “testing riding them”

What is vibe-coding?

As with lots of terminology in the AI boom, defining vibe-coding is a bit nebulous. Different people (and bots!) use the term differently. For our purposes, let’s keep it simple:

Vibe-coding is a workflow where you describe what you want in natural language, an LLM writes the code, and you iteratively refine the result until you achieve the desired outcome in a reproducible way.

Caveats with vibe-coding

Vibe-coding can be incredibly productive, but it comes with risks.

If you don’t understand what the code is doing, you may:

  • fail in the trap of intellectual laziness
  • accept incorrect results in which is the logic does not make sense
  • use inappropriate statistical or analytical methods

Some final thoughts

Reviewing the code

  • Despite the temptation, we are going to need to be disciplined about reading the code and ensure that we understand exactly what it is doing.

  • As noted, I have a STYLE.MD guide that writes the code in my style. That helps me review/evaluate the code quicker.

Learning new coding tips

  • Reading the code that the Agent wrote introduced me to new functions/approaches to making new maps

Goes beyond spatial data

  • Obviously, vibe-coding is not restricted to spatial data and you can implement the same approach to other type of data.

Homogensing workflow

An emerging question that we are wondering about (and we mentioned in module 1…sorry to dwell) is what does this mean for how we tackle these steps in the future and our workflows.

  • How homogenized do our workflows become? Standardised ARI STYLE.MD, WOKFLOW.MD, and set of SKILLS.MD files/folders.

  • Do we have a project folder that has a similar structure so both humans and a local LLM that has been trained on our workflow can easily understand it, revise, and QC it?

  • Sure seems apt given all the discussion on templates/standardisation

Reproducibility

  • An obvious strength is that we have a history of what was done…(the R script is right there, all the data files (untouched!!!!) )
